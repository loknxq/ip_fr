# Vinyl Collection Service — ПР10: Django Admin и ORM (тема сохранена)

**Индивидуальная тема: коллекционирование виниловых пластинок.** Приложение
продолжает собственный проект ПР1–ПР9, а не заменяет его учебным примером Roomly.
Термины и сценарии из ПР10 адаптированы к моделям `Record` (пластинка),
`Collection` (коллекция), `CollectionRecord` (экземпляр пластинки в коллекции)
и `users.User` (участник предметной области). Исходные данные и старые URL сохранены.

**Новый этап ПР10:** русскоязычная Django Admin; таблицы, фильтры, поиск,
сортировка, ограничения доступа и inline; состояния экземпляров `TextChoices`,
миграция старых связей, собственный QuerySet, ORM-фильтры и статистика;
страницы по `slug`, `get_absolute_url()`, `GeneratedField`, контекстный
процессор, журнал экземпляров, Debug Toolbar и тесты.

[Отчёт ПР10](docs/REPORT_PR10.md) ·
[Чек-лист, 17 требований и 30 критериев](docs/PR10_CHECKLIST.md) ·
[Фактический протокол проверки](docs/VERIFICATION_PR10.txt)

**Важно о проверке:** исходная среда редактирования не содержит Django,
поэтому новые HTTP-тесты и `manage.py check` **не могли быть запущены** здесь.
Это отражено в протоколе; после установки `requirements.txt` выполните команды
из раздела «Проверка ПР10». Нельзя выдавать старые результаты ПР9 за новый прогон.


## Быстрый запуск из архива

Требуется Python 3.10 или новее и Django 5.2.x. В ПР9 ранее проверяли
Python 3.12.14 и Django 5.2.18; текущий этап ПР10 требует повторного запуска.
Откройте терминал в каталоге `ip_fr`, где находится `manage.py`.

### Windows (cmd)

```bat
python -m venv venv
venv\Scripts\activate
python -m pip install -r requirements.txt
python manage.py migrate
python manage.py import_pr7
python manage.py runserver
```

### Linux / macOS

```bash
python3 -m venv venv
source venv/bin/activate
python -m pip install -r requirements.txt
python manage.py migrate
python manage.py import_pr7
python manage.py runserver
```

Откройте http://127.0.0.1:8000/ . Готовый архив содержит уже заполненную `db.sqlite3`;
повторные `migrate` и идентичный `import_pr7` не дублируют записи.
До применения миграций ПР10 сделана резервная копия этой базы:
`data/db_before_pr10.sqlite3` (отдельно от исходной `data/vinyl.sqlite`).
`migrate` обновляет рабочую `db.sqlite3`, резервная копия не изменяется.
Виртуальное окружение из исходного архива не переносится: создайте его на своём компьютере.

При получении проекта только из Git локальных БД не будет. После `migrate`
наполните **пустую** базу сохранённой fixture вместо `import_pr7`:

```bash
python manage.py loaddata data/orm_fixture.json
python manage.py runserver
```

Fixture представляет проверенную выгрузку исходного набора ПР7. Она не предназначена
для объединения с изменёнными данными: `loaddata` может обновлять записи с теми же ID.
Для переноса из собственной старой базы используйте безопасную команду `import_pr7`.

## Страницы и сценарии

| URL | Назначение |
| --- | --- |
| `/` | Главная страница |
| `/records/` | Каталог, поиск, фильтрация, сортировка, по 5 пластинок на странице |
| `/records/<id>/` | Старый адрес карточки пластинки из ПР9 (сохранён) |
| `/records/<slug>/` | Новый постоянный адрес карточки, формируется `get_absolute_url()` |
| `/records/search/?q=Pink` | Сохранённая отдельная страница поиска |
| `/collections/` | Коллекции, их полный размер, поиск названия и фильтр по исполнителю |
| `/collections/<id>/` | Действующее содержимое коллекции (без выведенных экземпляров) |
| `/collections/placements/` | Журнал всех включений пластинок: состояния, фильтры, поиск, сортировка, пагинация |
| `/collections/placements/<id>/` | Карточка включения, две связанные модели через `select_related()` |
| `/collections/statistics/` | Общие показатели, годы выпуска, размеры коллекций, жанры |
| `/admin/` | Локализованная админ-панель с четырьмя моделями, inline, поиском и массовым изменением статусов |

Каталог принимает `q`, `scope=all/title/artist`, `genre`, `year_from`, `year_to`,
`collection`, `known_year=1`, `sort=title/artist/year/-year`, `page`.
Коллекции принимают `q`, `artist`, `page`.

**Журнал:** `/collections/placements/?collection=1&status=in_collection&sort=-year`
принимает `q`, `collection`, `status`, `available_only=on`, `year_from`,
`year_to`, `sort=collection/artist/year/-year`, `page`. `PlacementFilterForm`
валидирует значения и диапазоны. Разрешённая сортировка задаётся в словаре
`PLACEMENT_SORTS`; шаблон пагинации сохраняет GET-параметры.

**Состояния пластинки в коллекции (`CollectionRecord.Status`):**

- `IN_COLLECTION` — пластинка находится в коллекции и доступна для обмена;
- `RESERVED` — находится в коллекции, но зарезервирована (не для обмена);
- `REMOVED` — выведена из коллекции; запись остаётся в истории.

Менеджер `CollectionRecord.objects` предоставляет `.current()`,
`.available()`, `.reserved()`, `.removed()`, `.for_collection()`,
`.for_record()`, `.for_year()`. Старые 13 связей после `migrate`
получают `IN_COLLECTION` через миграцию данных `0002`, без удаления связей.
Статистика отдельно показывает исторические и действующие включения.

**Детали ПР10:** `Record.slug` автоматически транслитерируется при создании,
а при переименовании не меняется. Миграция присваивает старым записям
уникальные слаги с ID; старые числовые адреса продолжают открываться.
`Record.is_vintage` — хранимый `GeneratedField` SQLite: `True` для
года выпуска от 1900 до 1990 включительно, иначе `False`; после изменения
`year` значение получается из базы при `refresh_from_db()`.
Контекстный процессор `records.context_processors.vinyl_context`
передаёт название сайта и общее количество пластинок в навигацию.

**Django Admin:** `records.Record`, `collections_app.Collection`,
`collections_app.CollectionRecord`, `users.User` зарегистрированы по одному
разу с русскоязычными названиями. В карточках пластинок и коллекций
доступны `TabularInline` связанных включений; в реестре включений можно
массово переводить экземпляры в резерв, вернуть в коллекцию или вывести
из неё, не стирая историю. `users.User` не является учётной записью Django Auth.
Чтобы войти в `/admin/`, создайте собственную учётную запись:

```bash
python manage.py createsuperuser
```

**Опробовать ORM без изменения рабочей БД:**

```bash
python manage.py demo_pr10
```

Команда выводит действия `QuerySet`, связанные `F()`/`values()`, SQL,
`EXPLAIN QUERY PLAN`, URL и результат GeneratedField; операции происходят
в отменяемой транзакции. Для визуальной проверки SQL откройте
Django Debug Toolbar → SQL на страницах журнала и карточки экземпляра.

## Сохранённые возможности и отчёт ПР9

Все фильтры проверяются Django Forms. Неверные значения дают понятное сообщение и
пустой результат, а не ошибку сервера или частично применённый фильтр.
Сортировка использует только словарь разрешённых полей.
Изменение формы сбрасывает номер страницы; ссылки пагинации сохраняют остальные GET-параметры.
Несуществующая карточка возвращает HTTP 404. Пустая коллекция остаётся в списке и статистике.

Поиск буквальный и регистронезависимый: для ASCII в каталоге применяется `icontains`,
для кириллицы — `iregex` с `re.escape`; название коллекции и исполнитель в фильтре
коллекций также ищутся через экранированный `iregex`. Пользовательский текст не
интерпретируется как SQL или произвольное регулярное выражение.

Статистика считает каждую пластинку один раз в каталоге и каждую связь отдельно.
Поэтому общее число включений может превышать число пластинок. Годы `0`/`NULL`
не участвуют в минимуме, максимуме и среднем. Пустые/NULL жанры объединяются
в группу «Не указан». Фильтр исполнителя у коллекций не уменьшает отображаемый
полный размер найденной коллекции.

## Модели и связи

| Модель | Поля и ограничения |
| --- | --- |
| `records.Record` | `id`: BigAutoField; `title`, `artist`: CharField(255); `genre`: CharField(255), blank/NULL; `year`: PositiveIntegerField, blank/NULL, default=0 |
| `collections_app.Collection` | `id`: BigAutoField; `name`: CharField(255); `records`: ManyToManyField через CollectionRecord |
| `collections_app.CollectionRecord` | `id`: BigAutoField; два ForeignKey: `collection`, `record`; уникальная пара внешних ключей |
| `users.User` | `id`: BigAutoField; `name`: CharField(255); `email`: EmailField(254) |

`CollectionRecord.collection` и `.record` используют `on_delete=CASCADE`:
при удалении коллекции удаляются её связи, а сами пластинки остаются.
При удалении пластинки коллекции сохраняются. Дубликат пары запрещён ограничением БД.
Обратные связи: `Collection.record_links`, `Record.collection_links`, `Record.collections`.

`Record.year` принимает `0`/`None` для неизвестного года либо 1900–текущий год.
Валидатор применяется в формах/admin, при `full_clean()` и при импорте.
Ограничение БД дополнительно запрещает отрицательные годы и годы 1–1899.
Обычный `save()` Django самостоятельно `full_clean()` не вызывает; при ручном
создании в shell вызовите его перед сохранением.

`users.User` — исходная сущность предметной области, отдельно от `django.contrib.auth.User`.
В ПР7 таблицы не содержали владельца коллекции, поэтому такая связь не выдумывается.
Данные входа в админку относятся только к Django Auth.

Карточка пластинки использует `Prefetch("collection_links")` со статусным
ограничением и `select_related("collection")`; состав коллекции —
`select_related("record")`. Каждая карточка выполняет два основных запроса
на данные независимо от числа связанных элементов, плюс отдельный `COUNT(*)`
общего контекстного процессора ПР10.

## Миграции и стратегия переноса

Выбран вариант 2 из методички: новые управляемые Django таблицы в `db.sqlite3`,
перенос из неизменяемого источника `data/vinyl.sqlite`.
Таблицы: `records_record`, `collections_app_collection`,
`collections_app_collectionrecord`, `users_user`.

Миграции сохранены в репозитории:

- `records/migrations/0001_initial.py`;
- `collections_app/migrations/0001_initial.py`;
- `users/migrations/0001_initial.py`.

В архиве сохранены исходная база и её резервная копия `data/vinyl_backup.sqlite`.
Они совпадают побайтно. `DATABASES` указывает на `db.sqlite3`, не на источник.
Исходная и целевая БД, а также резервная копия не отслеживаются текущей версией Git;
в истории предыдущих практических сохранены старые коммиты. Для воспроизведения
из Git включены миграции и `data/orm_fixture.json`.

```bash
python manage.py import_pr7 --source data/vinyl.sqlite
python manage.py import_pr7 --source data/vinyl.sqlite --check-only
```

Импорт читает SQLite в режиме `mode=ro`, валидирует данные, сохраняет исходные ID
и все пары связей. Запись выполняется через ORM в `transaction.atomic()`.
Идентичные записи пропускаются. При конфликте значений, битой ссылке, дубле или
ошибке валидации вся операция отменяется; данные не перезаписываются.
`--check-only` проверяет полный перенос с последующим откатом.

Результат переноса: **10 пластинок, 5 коллекций, 2 пользователя, 13 связей**.
Сверены все ID, поля и пары внешних ключей, а не только количества.
Fixture содержит 30 объектов: 10 + 5 + 2 + 13.

## SQL-панель и связанные поля для защиты

В `requirements.txt` включён `django-debug-toolbar==6.2.0`. После установки
зависимостей и `python manage.py runserver` на локальных страницах доступна
свёрнутая панель **DJDT**. Откройте её и выберите **SQL**.

- На `/collections/1/` покажите запрос с `select_related("record")` и JOIN.
- На `/collections/statistics/` найдите запрос таблицы «Состав коллекций»:
  `annotate(collection_name=F("collection__name"), ...)` получает связанные
  значения, а `values(...)` выбирает семь нужных полей словарями. SQL содержит
  JOIN обеих таблиц и псевдонимы `collection_name`, `record_title`,
  `record_artist`, `record_year`.
- В этой словарной проекции `select_related()` не нужен: пути в `F()` уже
  формируют JOIN. Каждая строка таблицы используется шаблоном и содержит ссылки
  на коллекцию и пластинку. Все связи доступны через пагинацию.

Настроены приложение, middleware, URL `__debug__/`, локальные `INTERNAL_IPS`
и JavaScript MIME type для Windows. Панель подключается при `DEBUG=True`;
в обычном запуске тестов отключена. Снаружи локальных адресов и при `DEBUG=False`
панель не выдаётся. Оставлены панели версий, времени, SQL, шаблонов и статики.

Серверная проверка подтверждает загрузку содержимого SQL-панели по AJAX,
наличие JOIN и псевдонимов; визуальный показ в браузере остаётся отдельным шагом.
Эта доработка закрывает программную часть пунктов 14, 15, 19, 20 таблицы
оценивания §7.3. Полная сверка всех 30 показателей приведена в чек-листе.

**Исторический результат ПР9 до текущих доработок:** в прежней среде
`check` без замечаний, **81 тест и 44 вложенные проверки были пройдены**,
