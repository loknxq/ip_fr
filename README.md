# Vinyl Collection Service — ПР9: Django ORM

Учебный сервис для каталога виниловых пластинок, тематических коллекций и списка пользователей.
Продолжен исходный проект ПР1–ПР7. Веб-приложение использует Django ORM,
сохраняет прежние адреса страниц и исходные данные.

## Быстрый запуск из архива

Требуется Python 3.10 или новее. Проверено с Python 3.12.14 и Django 5.2.18.
Откройте терминал в каталоге `ip_fr`, где находится `manage.py`.

### Windows (cmd)

```bat
python -m venv venv
venv\Scripts\activate
python -m pip install -r requirements.txt
python manage.py migrate
python manage.py import_pr7
python manage.py runserver
```

### Linux / macOS

```bash
python3 -m venv venv
source venv/bin/activate
python -m pip install -r requirements.txt
python manage.py migrate
python manage.py import_pr7
python manage.py runserver
```

Откройте http://127.0.0.1:8000/ . Готовый архив содержит уже заполненную `db.sqlite3`;
повторные `migrate` и идентичный `import_pr7` не дублируют записи.
Виртуальное окружение из исходного архива не переносится: создайте его на своём компьютере.

При получении проекта только из Git локальных БД не будет. После `migrate`
наполните **пустую** базу сохранённой fixture вместо `import_pr7`:

```bash
python manage.py loaddata data/orm_fixture.json
python manage.py runserver
```

Fixture представляет проверенную выгрузку исходного набора ПР7. Она не предназначена
для объединения с изменёнными данными: `loaddata` может обновлять записи с теми же ID.
Для переноса из собственной старой базы используйте безопасную команду `import_pr7`.

## Страницы и сценарии

| URL | Назначение |
| --- | --- |
| `/` | Главная страница |
| `/records/` | Каталог, поиск, фильтрация, сортировка, по 5 пластинок на странице |
| `/records/<id>/` | Карточка пластинки и коллекции, в которые она входит |
| `/records/search/?q=Pink` | Сохранённая отдельная страница поиска |
| `/collections/` | Коллекции, их полный размер, поиск названия и фильтр по исполнителю |
| `/collections/<id>/` | Содержимое коллекции |
| `/collections/statistics/` | Общие показатели, годы выпуска, размеры коллекций, жанры |
| `/admin/` | Создание, изменение и удаление записей через Django Admin |

Каталог принимает `q`, `scope=all/title/artist`, `genre`, `year_from`, `year_to`,
`collection`, `known_year=1`, `sort=title/artist/year/-year`, `page`.
Коллекции принимают `q`, `artist`, `page`.

Все фильтры проверяются Django Forms. Неверные значения дают понятное сообщение и
пустой результат, а не ошибку сервера или частично применённый фильтр.
Сортировка использует только словарь разрешённых полей.
Изменение формы сбрасывает номер страницы; ссылки пагинации сохраняют остальные GET-параметры.
Несуществующая карточка возвращает HTTP 404. Пустая коллекция остаётся в списке и статистике.

Поиск буквальный и регистронезависимый: для ASCII в каталоге применяется `icontains`,
для кириллицы — `iregex` с `re.escape`; название коллекции и исполнитель в фильтре
коллекций также ищутся через экранированный `iregex`. Пользовательский текст не
интерпретируется как SQL или произвольное регулярное выражение.

Статистика считает каждую пластинку один раз в каталоге и каждую связь отдельно.
Поэтому общее число включений может превышать число пластинок. Годы `0`/`NULL`
не участвуют в минимуме, максимуме и среднем. Пустые/NULL жанры объединяются
в группу «Не указан». Фильтр исполнителя у коллекций не уменьшает отображаемый
полный размер найденной коллекции.

## Модели и связи

| Модель | Поля и ограничения |
| --- | --- |
| `records.Record` | `id`: BigAutoField; `title`, `artist`: CharField(255); `genre`: CharField(255), blank/NULL; `year`: PositiveIntegerField, blank/NULL, default=0 |
| `collections_app.Collection` | `id`: BigAutoField; `name`: CharField(255); `records`: ManyToManyField через CollectionRecord |
| `collections_app.CollectionRecord` | `id`: BigAutoField; два ForeignKey: `collection`, `record`; уникальная пара внешних ключей |
| `users.User` | `id`: BigAutoField; `name`: CharField(255); `email`: EmailField(254) |

`CollectionRecord.collection` и `.record` используют `on_delete=CASCADE`:
при удалении коллекции удаляются её связи, а сами пластинки остаются.
При удалении пластинки коллекции сохраняются. Дубликат пары запрещён ограничением БД.
Обратные связи: `Collection.record_links`, `Record.collection_links`, `Record.collections`.

`Record.year` принимает `0`/`None` для неизвестного года либо 1900–текущий год.
Валидатор применяется в формах/admin, при `full_clean()` и при импорте.
Ограничение БД дополнительно запрещает отрицательные годы и годы 1–1899.
Обычный `save()` Django самостоятельно `full_clean()` не вызывает; при ручном
создании в shell вызовите его перед сохранением.

`users.User` — исходная сущность предметной области, отдельно от `django.contrib.auth.User`.
В ПР7 таблицы не содержали владельца коллекции, поэтому такая связь не выдумывается.
Данные входа в админку относятся только к Django Auth.

Карточка пластинки использует `prefetch_related("collections")`, состав коллекции —
`select_related("record")`. Каждая карточка выполняет два запроса независимо от
числа связанных элементов.

## Миграции и стратегия переноса

Выбран вариант 2 из методички: новые управляемые Django таблицы в `db.sqlite3`,
перенос из неизменяемого источника `data/vinyl.sqlite`.
Таблицы: `records_record`, `collections_app_collection`,
`collections_app_collectionrecord`, `users_user`.

Миграции сохранены в репозитории:

- `records/migrations/0001_initial.py`;
- `collections_app/migrations/0001_initial.py`;
- `users/migrations/0001_initial.py`.

В архиве сохранены исходная база и её резервная копия `data/vinyl_backup.sqlite`.
Они совпадают побайтно. `DATABASES` указывает на `db.sqlite3`, не на источник.
Исходная и целевая БД, а также резервная копия не отслеживаются текущей версией Git;
в истории предыдущих практических сохранены старые коммиты. Для воспроизведения
из Git включены миграции и `data/orm_fixture.json`.

```bash
python manage.py import_pr7 --source data/vinyl.sqlite
python manage.py import_pr7 --source data/vinyl.sqlite --check-only
```

Импорт читает SQLite в режиме `mode=ro`, валидирует данные, сохраняет исходные ID
и все пары связей. Запись выполняется через ORM в `transaction.atomic()`.
Идентичные записи пропускаются. При конфликте значений, битой ссылке, дубле или
ошибке валидации вся операция отменяется; данные не перезаписываются.
`--check-only` проверяет полный перенос с последующим откатом.

Результат переноса: **10 пластинок, 5 коллекций, 2 пользователя, 13 связей**.
Сверены все ID, поля и пары внешних ключей, а не только количества.
Fixture содержит 30 объектов: 10 + 5 + 2 + 13.

## Создание, изменение и удаление (CRUD)

Создайте собственную учётную запись администратора:

```bash
python manage.py createsuperuser
```

Откройте `/admin/`. Доступны все четыре модели; состав коллекции редактируется
через вложенные строки пластинок. Общего заранее заданного пароля нет.

Для демонстрации операций без изменения пользовательского каталога:

```bash
python manage.py demo_orm
```

Команда показывает `create()`, `get()`, изменение полей и `save()`, `delete()`,
прямые и обратные связи. Все демонстрационные изменения откатываются транзакцией,
в том числе при ошибке. Эти учебные операции не включены в подсчёт 15 рабочих выборок.

## Проверки

```bash
python manage.py check
python manage.py makemigrations --check --dry-run
python manage.py showmigrations
pytest -v
flake8 . --extend-exclude=venv
```

Результат: `check` без замечаний, пропущенных миграций нет, все миграции применены;
**76 тестов и 44 вложенных проверки пройдены**, `flake8` без замечаний.
Из них 25 тестов прежней ООП-версии сохранены. Новые тесты проверяют модели, CRUD,
миграции тестовой базы, импорт/откат/дубликаты, выборки, статистику, страницы,
пагинацию, Unicode, ошибочные и пустые данные, отсутствие N+1 у карточек.

`pytest` работает без дополнительного плагина: `conftest.py` настраивает Django,
создаёт отдельную тестовую базу через `setup_databases()` и удаляет её в конце.
Рабочая `db.sqlite3` не используется для тестовых записей.

Страницы проверены Django Test Client. Визуальную проверку в настоящем браузере
в среде подготовки выполнить не удалось: запуск Chromium ограничен окружением,
а облачный браузер не подключён к локальному серверу. Для завершения проверки
интерфейса на своём компьютере выполните короткий сценарий в `docs/PR9_CHECKLIST.md`.

## Структура проекта

| Путь | Назначение |
| --- | --- |
| `vinyl_project/` | Настройки Django, корневые URL, WSGI/ASGI |
| `homepage/` | Главная страница, обработчик 404 |
| `records/` | Модель пластинки, формы фильтрации, ORM views и шаблоны |
| `collections_app/` | Коллекции, M2M-связи, статистика, команды переноса и демонстрации |
| `users/` | Модель пользователя предметной области и админка |
| `templates/`, `static/` | Общие шаблоны, пагинация, локальные CSS/JS |
| `data/orm_fixture.json` | Воспроизводимая выгрузка исходных данных для ORM |
| `tests/` | Сохранённые ООП-тесты и новые тесты Django |
| `docs/` | Чек-лист, запросы, отчёт, результаты проверок |
| `main.py`, `models/`, `storage.py`, `utils.py` | Сохранённая консольная ООП-версия ПР1–ПР4 |
| `db/`, `sql/` | Сохранённая реализация SQL-слоя ПР7 |

`python main.py` запускает прежнюю консольную версию с JSON-данными. Она сохранена
как результат предыдущих практических и не подключена к текущим Django views.
Изменения её JSON-файлов не синхронизируются с ORM автоматически.
Рабочие веб-страницы не импортируют прежние SQL-модули; прямой `sqlite3` в новом
коде применяется только для чтения источника в `import_pr7`.
