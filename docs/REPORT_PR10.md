## 3. Административная панель Django

Административная панель подключена по `/admin/` с обычной системой аутентификации Django и русским языком `LANGUAGE_CODE="ru-ru"`. Названия приложений задаются через `AppConfig.verbose_name`, модели и поля имеют русскоязычные `verbose_name`, объекты — методы `__str__`. Все доменные модели зарегистрированы **по одному разу**:

| Модель | Настройки списка и интерфейса |
| --- | --- |
| `Record` | ID, название, исполнитель, жанр, год, `is_vintage`, число действующих коллекций; поиск по названию/исполнителю; фильтры по жанру, году и вычисляемому признаку; редактирование жанра в списке; inline экземпляров по коллекциям. |
| `Collection` | ID, название, количество действующих экземпляров (аннотация `Count`); поиск, сортировка, inline входящих пластинок. |
| `CollectionRecord` | Коллекция, пластинка, состояние, год выпуска; поиск по **полям связанных моделей** `collection__name`, `record__title`, `record__artist`; фильтры по состоянию, коллекции и жанру; сортировка, изменение статуса в списке, групповые действия резервирования/возврата/вывода. |
| `users.User` | ID, имя, электронная почта, поиск и сортировка; это **участник предметной области**, не учётная запись для входа в Django Admin. |

Размер страницы списков Admin — 20 записей. Для карточек `Record` и `Collection` добавлены `TabularInline` с `autocomplete_fields`; для списка связей настроен `list_select_related=("collection", "record")`. Обычные права Django используются для разграничения просмотра, создания, изменения и удаления. Тест описывает группу «Операторы пластинок» без разрешения на удаление. Учётные записи администратора с известным паролем в поставку не включены: их нужно создавать локально через `createsuperuser`.

## 4. Модели, миграции и собственный QuerySet

**Состояния экземпляра.** В `collections_app.models.CollectionRecord` добавлено `status` с `TextChoices`:

| Значение | Смысл | Учитывается в текущем составе | Доступна для обмена |
| --- | --- | --- | --- |
| `IN_COLLECTION` | В коллекции | Да | Да |
| `RESERVED` | Зарезервирована | Да | Нет |
| `REMOVED` | Выведена из коллекции; история сохранена | Нет | Нет |

В `CollectionRecordQuerySet` реализованы `.current()`, `.available()`, `.reserved()`, `.removed()`, `.for_collection()`, `.for_record()`, `.for_year()`. Менеджер подключён как `CollectionRecord.objects`. При переходе старых данных используется **миграция `collections_app/migrations/0002_collectionrecord_status.py` с `RunPython`**: существующие связи со значением `NULL` превращаются в `IN_COLLECTION`. Это соответствует смыслу исходных записей ПР9 и не удаляет историю.

**Постоянная ссылка пластинки.** В `records.Record` введено уникальное `slug`, генерация для латиницы и кириллицы, обработка одинаковых названий и метод `get_absolute_url()` с `reverse("records:record_by_slug")`. Ранее существовавшие записи получают адреса с суффиксом своего ID в миграции `records/migrations/0002_record_slug_and_vintage.py`. Старый маршрут `/records/<int:record_id>/` сохранён; новый маршрут `/records/<slug:slug>/` добавлен без замены старого. При переименовании ранее сформированный адрес не изменяется.

**Вычисляемое поле.** `Record.is_vintage` — `GeneratedField` с `db_persist=True`; по выражению `CASE WHEN 1900 <= year <= 1990 THEN TRUE ELSE FALSE` SQLite хранит признак классического издания. Граница выбрана для предметной области винила, а не перенесена из примера о вместимости помещений. После изменения `year` заново полученное значение должно пересчитаться на стороне БД. Независимая проверка выражения в SQLite выполнена; применение Django-миграции и автоматизированная HTTP-проверка требуют наличия Django (см. раздел 8).

**Импорт и восстановление.** Сохранён исходный импорт `import_pr7`, который работает транзакционно и читает старую SQLite только на чтение. Для совместимости с ПР10 исправлено сравнение при повторном импорте: вычисляемый в БД `is_vintage` и автоматически созданный `slug` не считаются ложными конфликтами с данными исходного ПР7. `data/orm_fixture.json` содержит 30 объектов и десять непустых уникальных `slug`. Сохранены оригинальные базы и два независимых резервных источника:
`data/vinyl_backup.sqlite` для базы ПР7 и `data/db_before_pr10.sqlite3`
для целевой базы ПР9 до применения новых миграций.

## 5. Django ORM: фильтрация, сортировка, связанные модели и статистика

**Каталог пластинок** (`/records/`) и прежний поиск продолжают применять валидируемые параметры `q`, `scope`, `genre`, `year_from`, `year_to`, `collection`, `known_year`, `sort`, `page`. К запросам по коллекции добавлено условие `CollectionRecord.Status.IN_COLLECTION`/`RESERVED`, исключающее выведенные экземпляры. Объекты отсутствующей карточки обрабатываются `get_object_or_404` → HTTP 404. Для загрузки коллекций пластинки применяется `prefetch_related` со статусным ограничением.

**Реестр экземпляров** (`/collections/placements/`) — новая таблица предметной области с поиском по названию, исполнителю и коллекции; фильтрами `collection`, `status`, `available_only`, `year_from/year_to`; сортировкой по коллекции, исполнителю, году вверх/вниз; пагинацией по пять записей. Входные параметры разбирает `PlacementFilterForm`, сортировка ограничена словарём `PLACEMENT_SORTS`; неверные значения не становятся сырой частью запроса. GET-параметры сохраняются на следующей странице через `{% querystring page=... %}`.

Для получения данных связанных моделей используется один QuerySet с `annotate` и `F`, например:

```python
CollectionRecord.objects.annotate(
    collection_name=F("collection__name"),
    record_title=F("record__title"),
    record_artist=F("record__artist"),
    record_year=F("record__year"),
).values("id", "collection_id", "record_id", "status",
         "collection_name", "record_title", "record_artist", "record_year")
```

Для страницы отдельного экземпляра (`/collections/placements/<id>/`) используется `select_related("record", "collection")`; оба внешних ключа загружаются совместно. В `statistics()` используются `aggregate(Count, Min, Max, Avg)`, `annotate(Count(..., filter=Q(...)))`, `exclude`, `Coalesce`, `NullIf`, `values`, `order_by`; историческое число связей отличается от числа действующих, резервов и выведенных экземпляров. Пустые коллекции по-прежнему присутствуют в статистике.

## 6. Проверка логики доступности по состояниям

У исходного индивидуального проекта **нет бронирований помещений и даты занятия комнаты**. Поэтому нет оснований выдумывать модель Booking или вводить бизнес-правила Roomly; ближайший реальный аналог — доступность экземпляра винила для обмена. Логика отделяет присутствие пластинки в коллекции от её доступности:

- `objects.current()` включает `IN_COLLECTION` и `RESERVED` и исключает `REMOVED`;
- `objects.available()` включает **только `IN_COLLECTION`**;
- перевод из `IN_COLLECTION` в `RESERVED` убирает экземпляр из выдачи доступных, но оставляет в составе коллекции;
- перевод в `REMOVED` скрывает экземпляр из текущего состава, но сохраняет запись в журнале и исторических показателях;
- возврат статуса `IN_COLLECTION` делает экземпляр снова доступным без создания дубля связи.

Эта логика применяется в представлениях, статистике и административных действиях. Подготовлены автоматизированные тесты на изменение статусов и пользовательскую фильтрацию. **Их выполнение в среде подготовки не подтверждено** из-за отсутствия Django.

## 7. Проверка SQL и оптимизация связанных данных

В конфигурации сохранена Django Debug Toolbar (`django-debug-toolbar==6.2.0` в зависимостях). При `DEBUG=True` и локальном доступе она подключается к страницам; в тестовом режиме отключена. Вкладка **SQL** предназначена для просмотра фактических запросов в реальном браузере.

Ожидаемая картина по программной реализации:

1. **Страница реестра:** `COUNT(*)` для количества страниц и один `SELECT` на текущие строки с `JOIN` к таблицам коллекции и пластинки. `F()` и `values()` выбирают связанные значения прямо в SQL, поэтому дополнительный `select_related()` здесь не нужен.
2. **Карточка экземпляра:** один `SELECT` с `JOIN` обеих связанных таблиц через `select_related("record", "collection")`, вместо отдельных запросов на каждую связь.
3. **Карточка пластинки:** `prefetch_related` выполняет отдельный запрос для M2M вместо N+1 на каждую коллекцию.
4. **Контекстный процессор:** отдельный `COUNT(*)` пластинок для общей навигации — намеренный запрос; его следует учитывать при сравнении количества SQL-запросов.

Запросы и план можно получить безопасной демонстрационной командой `python manage.py demo_pr10`, которая работает в транзакции с откатом. **Фактический снимок Django Debug Toolbar не создан:** Django в имеющейся среде не установлен. Не следует выдавать ожидаемый SQL или изображение, построенное без запуска приложения, за измерение в панели.
